- actionType 삭제
어차피 작업에 대한 모든 판단은 Provisioner가 진행할 것이기 때문

- requestedAt 로그로 처리
스트림 내부에는 데이터가 차례대로 쌓이기 때문에 requestedAt이 필요하지 않음
이건 웹사이트 서버에서 로그로 볼 수 있게만 하면 된다.

- userId 대신 UUID로 대체
userId를 빼고 UUID를 넣게 설정
추후에 nimda-redis에서 user-UUID, UUID-접근 url로 정보를 관리할 것이기 때문

유저는 한번에 하나의 인스턴스만 할당 받을 수 있고
다시 할당 받기 위해서는 expiredAt이 되어야 한다.
따라서 유저가 같은 문제에 대해 2번 요청을 보낼 때 인스턴스가 2개 생기는 일은 없음
아직 구현하지는 않고 나중에 추가할 예정임

uuid로 한 이유는 다른 사용자가 접근하는 것을 막는 보안적인 조치이며
만약 user-challenge로 uuid를 만들 수 있다면 그렇게 하는 것이 좋음

#### 최종 요청 메시지 구조
uuid - 요청에 대한 구분
challengeCode - s3에서 문제 정보를 찾기 위해 사용
challengeCategory - 문제 타입별 기능 세분화
isolationType - 유저마다 만들어야 하는지 이미 만들어진 인스턴스를 재사용할지 판단
flagType - DYNAMIC = ctf에서 생성

#### 결과 메시지 구조
uuid - 어느 요청에 대한 결과인지 구분
status - 요청에 대한 작업 결과(FAILED, SUCCESS)
message - status가 FAIL인 경우 오류 메시지 출력
host - 인스턴스 할당 시 접근 정보
port - 인스턴스 할당 시 접근 정보
expiredAt - 인스턴스 만료 시간 / 다운로드는 사용하지 않음
downloadUrl - 다운로드 링크 / 인스턴스 관련 작업은 사용하지 않음
